# PassAuth Architecture

PassAuth is a self-hosted, zero-knowledge password manager. The server stores only ciphertext and can never read vault contents, item names, or URLs.

## Components

| Component | Tech | Notes |
|---|---|---|
| `crates/core` | Rust | All crypto, item model, importers. One implementation shared by every client. |
| `crates/server` | Rust (axum, tokio, sqlx) | REST API + WebSocket sync, SMTP, admin. Serves the web vault. |
| `crates/core-wasm` | Rust → WebAssembly | `core` bindings for the web vault and extension. |
| `web/` | TypeScript, React, Vite | Web vault, embedded into the server binary. |
| `extension/` | TypeScript, Chrome MV3 | Login, autofill, TOTP, passkey provider. |
| `crates/core-ffi` | Rust → UniFFI | `core` bindings (Kotlin and Swift) for the native apps. |
| `android/` (stage 2) | Kotlin, Jetpack Compose | Android app; see "Android app" below. |
| `ios/` (stage 2) | Swift, SwiftUI | iOS app; see "iOS app" below. |

### Why Rust
- Memory-safe without a garbage collector: fast, small container, low RAM.
- The same crypto code compiles to WASM (browser, extension) and native libraries (iOS, Android), so there is exactly one audited implementation of the vault format.
- Mature, audited crates: RustCrypto (`argon2`, `chacha20poly1305`, `hkdf`, `x25519-dalek`, `ed25519-dalek`), `opaque-ke`, `webauthn-rs`, `lettre`.

## Cryptography

### Account keys
```
master password ─┐
                 ├─ Argon2id (m=128 MiB, t=3, p=1, salt=random 16 B per account)
secret key (optional per user, 128-bit, in Emergency Kit) ─ HKDF ─ XOR ─► Account Unlock Key (AUK)
AUK ─► decrypts Account Key (random 256-bit)
Account Key ─► decrypts X25519 keypair (sharing) + Ed25519 keypair (signing)
Vault Key (random 256-bit per vault) ─ wrapped by Account Key, or sealed to each member's X25519 key
Item Key (random 256-bit per item) ─ wrapped by Vault Key ─► encrypts item JSON
```
- Secret Key is **off by default**. Users turn it on in settings, and admins can require it via policy. Enabling it re-wraps the Account Key under a new AUK; no vault data is re-encrypted.
- Cipher: **XChaCha20-Poly1305** everywhere. No unauthenticated modes, no legacy fallbacks.
- AEAD associated data binds `{format_version, item_id, vault_id}`, so ciphertexts cannot be swapped between items or fields.
- The whole item (name, URLs, username, password, TOTP, passkeys, notes, fields) is one encrypted blob. Plaintext on the server is limited to IDs, type, timestamps, and sizes.
- Item JSON carries a `format` number (`ITEM_FORMAT` in `crates/core/src/item.rs`). Clients upgrade older items when they decrypt them and stamp the current format when they encrypt. The server can't read items, so schema changes never need a server migration. Format 2 (0.2.1): a website's URL match `default` follows the client's "Default URI match detection" setting; older items, saved when `domain` was the implicit default, read as `default`.
- KDF parameters are authenticated: clients enforce minimums and refuse to log in with weaker parameters than they already know.

### Authentication: OPAQUE (`opaque-ke`)
- The server never receives the password or a hash it could crack offline.
- OPAQUE's export key and the Secret Key together derive the AUK, so login and decryption keys stay independent.
- Sessions: access JWT (15 min) plus a **rotating** refresh token bound to the device, with reuse detection that revokes the device.
- 2FA: TOTP, email OTP, WebAuthn security keys, recovery codes. New-device login sends an email alert.

### Sharing (organizations)
- Vault keys are sealed to members' X25519 public keys.
- Public keys are shown as fingerprints for out-of-band verification, so a malicious server cannot silently substitute keys.
- Removing a member rotates the vault key, and items are re-encrypted lazily.

## Features (stage 1: server + extension)
- Item types: Login (multiple URLs, TOTP, passkeys), Secure Note, Card, Identity, SSH Key. Plus custom fields, folders, favorites, trash, password history, attachments.
- Password and passphrase generator; breach check via HIBP k-anonymity, run from the client only.
- **Import** (client-side only; plaintext never reaches the server): export files from other password managers (JSON, password-protected JSON, CSV, `.1pux`, KDBX). Formats and field mappings: `docs/IMPORT_FORMATS.md`. **Export**: encrypted PassAuth JSON plus plaintext JSON/CSV.
- SMTP: verification, invites, new-device alerts, email 2FA, recovery, admin test mail.
- Admin panel: off by default, Argon2-hashed token, no shell or executable-path settings.
- Real-time sync over WebSocket (`/api/ws`), plus a revision-date check for cheap polling.
- Website icons: `GET /api/icons/{host}` (unauthenticated, used as `<img src>`; clients fall back to a letter avatar on error). The server fetches the site's `<link rel=icon>` or `/favicon.ico` defensively: public DNS names only, every resolved IP must be public and the connection is pinned to it, redirects re-validated (max 3), ports 80/443, 5 s budget, 100 KiB cap, only PNG/ICO/GIF/JPEG/WebP by magic bytes (never SVG/HTML), `CSP: default-src 'none'`. Hits cached 7 days, misses 1 day (`ICON_CACHE_DIR`, default `icons/` beside the SQLite file). Uncached fetches are rate-limited per client IP (60/min) and capped at 8 concurrent. `ICON_SERVICE=off` disables it. Privacy: the server learns which sites' icons are requested (not which user, not vault contents); turn it off if that matters.
- Extension: login to any PassAuth server URL; autofill only on user action, in the top-level same-origin frame; inline save prompts; TOTP codes; acts as a WebAuthn **passkey provider** (ES256 keys stored inside the encrypted item, with fallback to browser or hardware keys).

## Android app (`android/`)
- Gradle project with two modules. `:core` is an Android library holding the UniFFI bindings (`io.passauth.core`) and `libpassauth_ffi.so` (arm64-v8a, x86_64), both generated by `scripts/build-android-core.sh` and gitignored, plus JNA. `:app` is the app (`io.passauth.app`, minSdk 34, compile/target 36). Crypto only ever comes from the Rust core; items, bundles and KDF params cross as JSON in the server/web shape (`app/.../data/Item.kt` mirrors `web/src/lib/types.ts`).
- Build: `scripts/build-android-core.sh && cd android && ./gradlew :app:assembleDebug :app:testDebugUnitTest` (JVM tests don't load the native library). Release: `./gradlew :app:bundleRelease`, signed only when `ANDROID_UPLOAD_KEYSTORE_PATH`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `ANDROID_UPLOAD_KEY_ALIAS` and `ANDROID_UPLOAD_KEY_PASSWORD` are set. Debug builds use the `io.passauth.app.debug` id.
- Version: `versionName` = root `Cargo.toml` `[workspace.package] version`, `versionCode` = major·1 000 000 + minor·1 000 + patch (`android/buildSrc/src/main/kotlin/AppVersion.kt`, shared with the unit tests).
- Data layer (`app/.../data`): `VaultRepository` mirrors the extension's `background/vault.ts` (prelogin → OPAQUE → 2FA → bundle unlock → `/sync` → decrypt; create/update/trash; lock/logout; up to 5 accounts). `ApiClient` pins each request to one account and rotates refresh tokens on 401. `SecureStore` keeps tokens, settings and per-account data in a DataStore file encrypted with an Android Keystore AES-GCM key, plus an encrypted copy of the last `/sync` response (ciphertext) so the vault opens offline. Unlocked keys live only in memory as Rust handles.
- Unlock: master password (+ stored Secret Key), or biometrics: `Account.toSessionBytes()` (64 bytes) is wrapped by a per-account Keystore key that requires strong biometric auth and is invalidated when biometrics change. Vault timeout and action like the extension (`LockManager`); with "never" the session bytes are kept in the encrypted store.
- Hardening: no backup (`allowBackup=false`, extraction rules exclude everything), https only except `localhost`/`10.0.2.2` (network security config), `FLAG_SECURE` while unlocked or showing the Secret Key, clipboard copies marked sensitive and cleared after the user's delay, no secrets in logs.
- Autofill service (`app/.../autofill`, `PassAuthAutofillService`): `StructureParser` reads the AssistStructure (visible enabled text fields, `webDomain`/`webScheme`, only fields of the focused site's frame); `FieldClassifier` finds username/password/one-time-code fields from autofill hints, input type, HTML attributes and id/hint text (patterns of the extension's `fields.ts`). `FillTarget.resolve` decides what may match: web content in a browser on the privileged allowlist (package + signing cert) or in a WebView whose domain's asset links list the app → by website (`UrlMatcher`, default-match setting; scheme missing → https; Android gives no path, so "exact"/"starts with" see `scheme://domain/`); any other app → logins with the website `androidapp://<package>`; a browser's own UI and PassAuth itself → nothing. Web logins never match apps and vice versa; the extension's https→http downgrade refusal and "never fill/save on the PassAuth web vault" apply. Unlocked: one Dataset per login (drop-down + keyboard inline suggestions via `androidx.autofill`) plus "Open PassAuth". Locked: one "PassAuth is locked" entry whose authentication IntentSender opens `AutofillAuthActivity`, which unlocks (master password or biometrics) and returns the datasets in `EXTRA_AUTHENTICATION_RESULT`. Logins with a TOTP get per-dataset authentication: picking one runs `AutofillAuthActivity` (see-through, no UI when unlocked), which returns the filled Dataset with a fresh code (also filled into a one-time-code field) and copies it when "Copy verification code automatically" is on — the only reliable hook for running code at the moment of selection. Save: `SaveInfo` (password required, username optional, save when the form disappears, "Never" button → never-save list keyed by base domain or `androidapp://<package>`); `onSaveRequest` updates the same site+username login's password (old one kept in password history) or creates a login; locked → returns an IntentSender to unlock first (credentials stay in memory, never in the intent). Respects "Ask to save and update logins". Always the active account.
- Credential Manager provider (`app/.../credentials`, Android 14+, `androidx.credentials`): `PassAuthCredentialService` offers a `CreateEntry` for ES256/platform passkey requests, `PublicKeyCredentialEntry`s for matching passkeys (rpId, allowCredentials or discoverable) and `PasswordCredentialEntry`s (same matching as autofill); locked → an `AuthenticationAction`. `CredentialActivity` does the work after the user picks: origin check (`Origins`): privileged callers' origin from `CallingAppInfo.getOrigin(allowlist)` with `res/raw/privileged_allowlist.json` = Google Password Manager's published list (https://www.gstatic.com/gpm-passkeys-privileged-apps/apps.json, linked from the provider guide; Chrome stable/beta/dev/canary, Firefox, Edge, Brave, Samsung, …) and the RP ID checked against the origin like the extension's `effectiveRpId`; apps get `android:apk-key-hash:<b64url sha256(cert)>` and must be listed in `https://<rpId>/.well-known/assetlinks.json` (`delegate_permission/common.get_login_creds`, package + cert fingerprint; https, no redirects, 5 s, 256 KiB, cached 1 h; `include` not followed) or the request is refused. User verification: unlocking in the flow counts, otherwise BiometricPrompt (biometric or screen lock). excludeCredentials is checked after consent (InvalidStateError). Keys and signatures come from the core (`passkeyCreate`/`passkeyAssert`); clientDataJSON is built with `passkeyClientDataJson` for apps (and hashed), while browsers' `clientDataHash` is signed as given and the built JSON is only the placeholder the guide asks for. Responses are WebAuthn JSON; passkeys are stored like the extension's `storePasskey` (same fields, counter 0, discoverable), on the same site+username login or a new login for `https://<rpId>`.
- Settings → Autofill shows whether PassAuth is the autofill service and the passkey provider, with buttons to Android's settings, plus default URI match, TOTP copy, clipboard clearing, "Ask to save and update logins" and the never-save list. Debug-only test hooks (gradle properties, never in release builds): `passauth.testAssetLinksBase` (asset links from a local server) and `passauth.testPrivilegedApp` (trust one more browser, e.g. a Chromium snapshot). `:samples:login` is a debug-only test app (login form + Credential Manager calls), not part of the app or its bundle.
- Account deletion (Google Play requirement): Settings → About → Delete account. The master password is proven to the server with an OPAQUE login with `purpose: "reauth"` on the signed-in session (like the web vault's `reauth`), then `DELETE /api/account` with `x-reauth-token`; the account is then forgotten locally like Log out (biometric key, offline copy, stored Secret Key and two-step remember token removed; the last account keeps only the server address).
- Item editor TOTP field: type, "Paste" (clipboard) or "Scan QR code" (CameraX preview + ImageAnalysis, latest frame only, decoded in memory by ZXing core; no Play services; frames are never stored and the luminance buffer is wiped on close; the preview is a TextureView inside a dialog that inherits FLAG_SECURE). The `CAMERA` permission is requested only on tap; denial shows how to type or paste the key and a link to Android settings. `otpauth://totp/…` URIs are stored whole (scheme lower-cased for the core), plain base32 keys cleaned (upper case, no spaces); `OtpAuth` mirrors the core's TOTP checks so accepted keys always produce codes. HOTP and `otpauth-migration://` are refused with an explanation.
- Item page: "Password history" (count) opens the previous passwords (`password_history`, newest first, masked with reveal and copy). The overflow menu moves an item to another vault where the user is owner, admin or writer: re-encrypted with the target vault key under the same id and `PUT /api/items/{id}` with the new `vault_id` and the old revision (the web vault's `updateItem(entry, item, vaultId)`).
- Live sync (`LiveSync`): while MainActivity is started and the active account is unlocked, a WebSocket to `/api/ws?access_token=…` (OkHttp, 25 s pings). `{"type":"sync","revision":N}` with N above the shown revision re-syncs; `{"type":"logout"}` makes the app check its session (an ended one signs the account out through the refresh-token path). Disconnects on background, lock or account switch; reconnects with backoff (1 s doubling to 60 s, jitter), each time first calling `/sync/revision` so an expired access token is refreshed and missed changes are caught up. The item editor keeps the item as it was when editing started, so a live update during editing surfaces as the usual revision conflict instead of being overwritten.
- Export: Settings → Vault options → Export vault. Formats come from the core (`exportVaultEncrypted` (≥10-character export password, Argon2id), `exportVaultJson`, `exportVaultCsv` (logins and notes only)), with warnings for the unencrypted ones. The master password is checked locally against the bundle first; the file is written only to the location the user picks with `ACTION_CREATE_DOCUMENT` (`passauth-export-YYYY-MM-DD[-protected].json` / `.csv`).
- Web vault shortcuts open the account's server in the browser with path routes: Security → `/settings/two-step`, `/settings/security`; Vault options → `/settings/vaults`, `/import`, `/vault`.
- Accessibility: icon buttons have content descriptions, card titles and page titles are headings, label + value rows are read as one node before their actions, masked secrets read as "hidden", text drawn inside fixed shapes (avatar, TOTP ring) doesn't scale with the font, select fields wrap. Checked at font scale 2.0.

## iOS app (`ios/`)
- Xcode project generated by XcodeGen from `ios/project.yml` (`PassAuth.xcodeproj` is not committed). Targets: `PassAuthCore` (framework: the UniFFI Swift bindings `ios/Core/Sources/PassAuthCore.swift` plus the static `PassAuthCoreFFI.xcframework`, device arm64 + simulator arm64, both generated by `scripts/build-ios-core.sh` and gitignored), `PassAuthKit` (framework, extension-safe API only: the data layer, shared with the AutoFill extension), `PassAuth` (SwiftUI app, `io.passauth.app`, iOS 17+, iPhone and iPad), `PassAuthAutoFill` (credential provider extension `io.passauth.app.autofill`, embedded in the app; theme and form components come from `ios/UI`, compiled into both), `PassAuthTests` (XCTest, hosted) and `PassAuthUITests` (XCUITest). Swift 6 language mode with complete concurrency checking (the generated bindings build in Swift 5 mode). Crypto only ever comes from the Rust core; items, bundles and KDF params cross as JSON in the server/web shape (`Shared/Item.swift` mirrors `web/src/lib/types.ts`: lenient decoding, nulls written, unknown `format` omitted).
- Build: `scripts/build-ios-core.sh && cd ios && xcodegen generate && xcodebuild -scheme PassAuth -destination 'platform=iOS Simulator,name=iPhone 17' test`. Signing: automatic with `DEVELOPMENT_TEAM = JEXQBK3SQ5` in `project.yml` (`ios/Local.xcconfig`, gitignored, can override it locally). Release: `.github/workflows/ios.yml` archives on macOS with the App Store Connect API key (Admin; cloud-managed certificates via `-allowProvisioningUpdates`) and uploads with `ios/ExportOptions.plist` (app-store-connect, destination upload) on each `vX.Y.Z` tag or a manual run with "upload". `ITSAppUsesNonExemptEncryption = YES` (standard algorithms; France excluded in App Store Connect). Device signing also needs the App Group `group.io.passauth.app`, the Keychain group and the AutoFill credential provider capability on both App IDs (`io.passauth.app`, `io.passauth.app.autofill`).
- Version: XcodeGen's `preGenCommand` runs `ios/scripts/version.sh`, which writes `ios/Version.xcconfig` (gitignored) from the root `Cargo.toml`: `MARKETING_VERSION` = workspace version, `CURRENT_PROJECT_VERSION` = major·1 000 000 + minor·1 000 + patch (as Android's versionCode; `Shared/AppVersion.swift` mirrors it for the tests, which also check the built Info.plist against `Cargo.toml`).
- Data layer (`ios/Shared`): `VaultRepository` (`@MainActor`, `@Observable`) mirrors the Android repository and the extension's `vault.ts` (prelogin → OPAQUE → 2FA with remember-device → bundle unlock → `/sync` → decrypt; register; create/update/trash/restore/delete forever with revision conflicts reported as `ConflictError`; lock/logout; up to 5 accounts). Operations are serialised by an async lock; Argon2id and decryption run off the main thread. `ApiClient` (ephemeral `URLSession`, no cache/cookies, redirects refused) pins each request to one account and rotates refresh tokens on 401.
- Storage (`SecureStore`): accounts, settings and device id in `state.bin`, and each account's last `/sync` response in `vault/<id>.bin`, in the App Group container (`group.io.passauth.app`, falls back to Application Support without the entitlement), encrypted with ChaCha20-Poly1305 under a random Keychain key (file name as associated data), file protection complete, excluded from backup. Tokens, Secret Keys, two-step remember tokens and (vault timeout "never") session bytes live in one Keychain item. All Keychain items are `WhenUnlockedThisDeviceOnly`, non-synchronizable, in the shared access group `$(AppIdentifierPrefix)io.passauth.shared` listed in both targets' entitlements and copied into their Info.plist (`PAKeychainGroup`): `JEXQBK3SQ5.io.passauth.shared` when signed with the team, `io.passauth.shared` in unsigned simulator builds (the simulator honours the embedded entitlements). A missing `state.bin` (fresh install) deletes leftover Keychain items. The state is read once the UI is up.
- App ↔ extension (two processes on the same files and Keychain item): every `SecureStore.update` re-reads `state.bin` and the secrets under a cross-process `flock` (`.state.lock`, 2 s timeout) before writing, so neither side overwrites the other; the app calls `reload()` when it becomes active. Only the app creates the state, the store key or wipes them (`Role.appExtension` never does). Refresh tokens rotate and a reused one revokes the session, so a refresh runs under a per-account lock (`.refresh-<id>.lock`, 25 s wait, 20 s request), re-reads the tokens, and calls `/auth/refresh` only if the stored access token is still the rejected one (otherwise the other process already rotated them). The app holds that lock inside a background task (iOS kills apps suspended while holding a shared-container lock). A refresh that can't reach the server no longer signs the account out.
- Unlock: master password (+ stored Secret Key), or Face ID / Touch ID: `Account.toSessionBytes()` in a Keychain item with `SecAccessControl` `.biometryCurrentSet` (invalidated when enrolment changes; the app then turns biometric unlock off and asks for the master password). Vault timeout and action like the extension and Android (`LockManager`: continuous clock, touches tracked by a non-interfering window gesture recognizer, "Immediately" fires when the scene goes to the background, "On app restart" keeps keys in memory only, "never" keeps session bytes in the Keychain).
- Hardening: privacy cover over the window whenever the scene isn't active while unlocked or while the new Secret Key is shown; clipboard copies are `localOnly` (no Universal Clipboard) with `expirationDate` = the user's clearing delay; ATS https only with `NSAllowsLocalNetworking`, and the app accepts plain http only for local hosts (localhost, loopback, private IPv4, link-local, `.local`); no logging.
- UI (SwiftUI, native patterns with the brand: navy navigation bars, accent `#0866ED`/`#3D8BFF`, the logo drawn as a vector from `assets/passauth-logo.svg`, light/dark/system theme): sign-in (server, email, master password, Secret Key, two-step with remember device, create account with Emergency Kit export), unlock, TabView with Vault (search, filter menu: all/favorites/trash, type, folder, vault; swipe and context actions; pull to refresh; website icons from `/api/icons/{host}`), item page (copy, reveal, live TOTP with ring, open website, passkeys, restore/delete forever for trashed items), item editor sheet (all item types, labels above boxes, TOTP via typing, paste, camera or image, revision-conflict choice: keep mine or use the other version), Generator (core password/passphrase; options in the shared settings `Settings.generator`, so AutoFill generates with them; the old app-only user defaults are migrated once) and Settings (Account, Account security, AutoFill (status, ask to save and update logins, never-save list, default URI match, TOTP copy, clipboard clearing), Vault options, Appearance, About).
- AutoFill extension (`ios/AutoFill`, `ASCredentialProviderViewController`; capabilities ProvidesPasswords, ProvidesPasskeys, ProvidesOneTimeCodes (iOS 18), ShowsConfigurationUI; entitlement `com.apple.developer.authentication-services.autofill-credential-provider` on app and extension). Its own process: it opens the vault itself (master password, Face ID / Touch ID via the shared biometric Keychain item, or the kept session bytes of vault timeout "never") from the on-device copy of the last sync (shown at once, synced in the background), and forgets it when iOS ends the extension; it can't sign in. Matching (`AutofillMatcher`): iOS gives a page URL (Safari, `.URL`) or a domain (apps with associated domains, `.domain` → `https://<domain>/`, so "exact"/"starts with" see that), matched with `UrlMatcher` and the default-match setting like Android's web `FillTarget`; app websites (`androidapp://`) never match, an https login is never offered on an http page, nothing is filled on the account's own server origin. The list shows suggestions for the site, the other logins, search, and (passkey request) the RP's passkeys newest first; picking a login fills it and, with "Copy verification code automatically", copies the current TOTP (`localOnly`, expiring after the clearing delay). One-time codes (iOS 18): list of matching logins with a TOTP, `completeOneTimeCodeRequest`.
- Identity store (`CredentialIdentitySync` + `IdentityMapper`): after every sync, settings change (default match) and in the extension's configuration screen, the active account's logins replace the `ASCredentialIdentityStore` entries (only when PassAuth is enabled): passwords (`ASPasswordCredentialIdentity`), passkeys (`ASPasskeyCredentialIdentity`: RP ID, user name, credential ID, user handle) and TOTP logins (`ASOneTimeCodeCredentialIdentity`, iOS 18), with the item id as record identifier, never a secret; favorites rank higher. Websites map by their effective match: base domain → `.domain` identity of the base domain, host → `.URL` of the origin, exact / starts with → `.URL` of the address; regex, never, app and non-web websites and anything covering the server's host are left out (iOS matches identities itself and doesn't tell the extension the page when one is picked). Emptied on log out (also the timeout's) and when the active account after a switch or log out is locked; kept while locked (iOS shows the user names in the QuickType bar). A picked suggestion fills without UI only when the vault opens without the user (timeout "never") and the item is still there; otherwise `userInteractionRequired` → unlock UI → fill. Passkeys always go through the UI.
- Passkeys: registration (`prepareInterface(forPasskeyRegistration:)`) asks "Save a passkey?" for the RP ID and user name iOS verified, refuses non-ES256 requests, checks iOS 18 `excludedCredentials` after consent (`matchedExcludedCredential`), creates the key with the core's `passkeyCreate` (same format as the extension and Android), stores it like `storePasskey` (sync first; same site + user name's writable login, else a new login for `https://<rpId>`; iOS doesn't give the RP name or display name, so RP ID and user name stand in) and returns the attestation with the OS's `clientDataHash`. Assertion (identity from the sheet, or the list for `prepareCredentialList(for:requestParameters:)` honouring `allowedCredentials`) signs the given `clientDataHash` with `passkeyAssert`. User verification: unlocking in the flow counts, otherwise `LAContext` `.deviceOwnerAuthentication`.
- Extension memory: iOS caps credential provider extensions (around 120 MB, device dependent). Argon2id with the default 128 MiB costs a 151 MB peak in the app process (22.9 MB baseline, `KdfMemoryTests`) and 166 MB in the extension (37.8 MB with the unlock screen up; debug builds expose it to `AutoFillUITests`), so on devices master-password unlock is offered in the extension only if `os_proc_available_memory()` exceeds the account's `memory_kib` + 16 MiB; otherwise it asks for Face ID / Touch ID (enabled in the app) or points to the app. The simulator has no extension limit (`os_proc_available_memory` = 0, so it's allowed there).
- Settings → AutoFill shows whether PassAuth is enabled (`ASCredentialIdentityStore.getState`), "Turn on AutoFill" (iOS 18 `ASSettingsHelper.requestToTurnOnCredentialProviderExtension`) and "Open AutoFill settings" (`openCredentialProviderAppSettings`, app settings as fallback), plus default URI match, TOTP copy and clipboard clearing; becoming enabled re-writes the identities.
- Simulator: the iOS 27.0 runtime can't reach `com.apple.SafariFoundation.CredentialProviderExtensionHelper` (launchd_sim lookup fails for Safari, Apple's own agent and PassAuth alike), so the identity store doesn't work there: no QuickType suggestions, no identities in the passkey sheet, and the app reports AutoFill as off. Everything else runs on the simulator (`AutoFillUITests`: enable in Settings with the configuration UI, Safari password list → unlock → fill → TOTP pasted, passkey create and sign-in via "More from PassAuth…"); the identity store paths need a device (`TEST_RUNNER_PA_IDENTITY_STORE=1`).
- Account deletion (App Store guideline 5.1.1(v)): Settings → About → Delete account (its own page: warning, master password, Secret Key if not stored). Like Android: OPAQUE login with `purpose: "reauth"` on the signed-in session, `DELETE /api/account` with `x-reauth-token`, then the account is forgotten locally (biometric item, offline copy, Secret Key unless another account uses the email, two-step remember token, AutoFill identities; the last account keeps only the server address).
- Item editor TOTP: type, `PasteButton`, "Scan QR code" (`AVCaptureSession` + `AVCaptureMetadataOutput` `.qr`: the output decodes, the app never sees or keeps frames; camera permission asked only on tap, `NSCameraUsageDescription` = website/privacy.html Camera section; denial explains typing/pasting and links to Settings; no camera → notice) or "Choose image" (`PhotosPicker`, no library permission; decoded in memory with `CIDetector` QR, also inverted, `Shared/QrDecoder.swift`). Parsing as Android's `OtpAuth` (URIs kept whole, base32 cleaned, HOTP and `otpauth-migration://` refused).
- Item page: "Password history" (count) → previous passwords newest first, masked, reveal, copy (`password_history`; saving a changed password prepends the old one, max 20). "Move to another vault" (owner/admin/write targets): `VaultRepository.moveItem` → re-encrypt with the target vault key under the same id, `PUT /api/items/{id}` with the new `vault_id` and the old revision. The editor keeps the entry it started from in `@State` (the sheet is rebuilt on every sync), so a change from elsewhere surfaces as the revision conflict.
- Live sync (`App/LiveSync.swift`, pure parts in `Shared/LiveSyncProtocol.swift`): while the scene is active and the active account unlocked, `URLSessionWebSocketTask` to `/api/ws?access_token=…` on its own ephemeral session (open/close from the delegate, redirects refused), pings every 25 s. Messages, backoff (1 s → 60 s, 20% jitter, `/sync/revision` before each reconnect) and the "logout" session check as Android. Disconnects on background, lock, log out and account switch.
- Export: Settings → Vault options → Export vault. Formats from the core (`exportVaultEncrypted` ≥ 10-character password, `exportVaultJson`, `exportVaultCsv`), warnings for the unencrypted ones, master password checked locally against the bundle first, file kept in memory and written only where the user picks with `fileExporter` (`passauth-export-YYYY-MM-DD[-protected].json` / `.csv`); the copy the exporter stages in the app's temporary directory is deleted after export or cancel and at launch. The exporter is an in-process remote view: the scene stays active, so even vault timeout "Immediately" doesn't lock behind it (UI-tested); no grace period needed as on Android.
- Web vault shortcuts open the account's server in Safari with path routes: Account security → `/settings/two-step`, `/settings/security`; Vault options → `/settings/vaults`, `/import`, `/vault`.
- Accessibility: icon buttons labelled, masked secrets read as "hidden", label + value rows combined, fixed-shape text (avatar, TOTP ring) doesn't scale, button rows stack when they don't fit (`ViewThatFits`). Checked at Accessibility XXL (`testLargeText`).
- Tests: unit tests for OTP/QR parsing, export names and formats, live sync messages/backoff/URL, move request shape and password history (`Phase3Tests`), save decisions, password rules → generator and `saveLogin` against a recording fake server (`SaveGenerateTests`). `Phase3UITests` (needs the :8091 server; a QR image in Photos via `xcrun simctl addmedia`) acts as a second device through `UITests/TestServer.swift` (Rust core linked into the UI test bundle: register, 2FA, vaults, item edits). Registration is rate-limited (10/hour/IP): restart the throwaway server between many runs.
- Saving logins (iOS 26.2, capability `SupportsSavePasswordCredentials`; the deployment target stays iOS 17, everything behind `@available(iOS 26.2, *)`): Safari's "Use Strong Password?" panel then lists "Save in PassAuth", and after a sign-up / password change form is submitted iOS calls `performWithoutUserInteractionIfPossible(savePasswordRequest:)`. Not offered (cancelled as `userCanceled`) when "Ask to save and update logins" is off, the page's base domain is on the never-save list (`Settings.neverSave`, same key as the extension and Android), the page is the server's own web vault, the request has no website (app identifier) or no password, or for the `generatedPasswordFilled` event (the submit that follows brings the user name). Decision (`Shared/SaveLogic.swift`, as Android's `planSave`): a login matching the page (`AutofillMatcher.candidates`, default-match setting) with the same user name (case-insensitive) and the same password → nothing to do (completed); same user name, writable → update its password (`updateItem` puts the old one into `password_history`); only in a read-only vault → refused; otherwise a new login named after the host (without `www.`), website = page origin (`https://<domain>` for an app's associated domain), match "Default". Without UI only when the user already chose to save (`userInitiated`) and the vault opens by itself (timeout "never"); otherwise `userInteractionRequired` → `prepareInterface(for: ASSavePasswordRequest)` → unlock if needed → "Save this login?" / "Update the password?" with user name, revealable password, Save/Update, Not now, Never for this site. `VaultRepository.saveLogin` syncs first (so the plan uses the server's revisions; offline → error shown), then creates/updates; the identity store is rewritten by the sync and awaited (`CredentialIdentitySync.flush`, at most 3 s) before `completeSavePasswordRequest`.
- Password generation (iOS 26.2, `SupportsGeneratePasswordCredentials`, with UI by default): `performWithoutUserInteraction(generatePasswordsRequest:)` returns `ASGeneratedPassword`s (`.strong`, `.alphanumeric` when the strong one has symbols and the site doesn't require them, `.passphrase` when the rules accept it; the user's preferred type first) without touching the vault; `prepareInterface(for: ASGeneratePasswordsRequest)` shows a sheet (type picker, regenerate, "Use this password"). Rules: the password field's `passwordrules`, else Safari's quirks for the site, else the confirmation field's (`Shared/PasswordRules.swift`: `required`/`allowed` classes incl. custom `[…]`, `minlength`, `maxlength`, `max-consecutive`). They map onto the core generator: classes the site doesn't allow are turned off, required ones on, length = the user's clamped to the site's range; when the site allows only some special characters, the core's symbols are replaced by those (system CSPRNG); every result is checked against the rules (retried up to 50 times). Rules the core can't express (a required set no whole class covers, a maximum under 8, nothing usable) fall back to the user's settings (the sheet says so).
- Seen on the iOS 27.0 simulator (`AutoFillUITests` AF6–AF8, page `tests/e2e/site/ios-signup.html`): focusing a new-password field shows Safari's "Use Strong Password?" panel with "Save in PassAuth" and "Fill Strong Password"; filling calls `performWithoutUserInteraction(generatePasswordsRequest:)` (no unlock) and fills PassAuth's first result into both fields; submitting then opens PassAuth's save sheet (unlock → "Save this login?"). A typed password brings iOS's own "Save Password? Choose where to save" alert (PassAuth / Passwords / Not Now) first; choosing PassAuth opens the sheet ("Update the password?" for a known user). iOS never called `prepareInterface(for: ASGeneratePasswordsRequest)` there (the suggestion pill only reopens the panel), so the generation sheet is compiled but not seen yet. `ASCredentialIdentityStore` calls may never answer on that simulator: identity writes are awaited at most 3 s.
- Not yet: conditional passkey registration, iOS store CI. Camera scanning needs a device (the simulator has no camera).

## Deployment
- One container image `ghcr.io/fahed-alhammadi/passauth`, tagged `X.Y.Z`, `X.Y`, and `latest`, with multi-arch builds (amd64, arm64).
- `docker compose up` gives the server, with SQLite in `/data` by default and PostgreSQL optional via `DATABASE_URL`.
- Config via env or `*_FILE` secrets. See `.env.example`.

## CI/CD (GitHub Actions)
- `ci.yml`: fmt, clippy, tests, `cargo audit`, web and extension build and tests on every PR.
- `release.yml`: on tag `vX.Y.Z`, build and push the multi-arch image to GHCR, and attach the extension zip to the release.
- Stage 2: `ios.yml` (xcodebuild archive + upload to App Store Connect / TestFlight) and `android.yml` (signed bundle to the Play Console internal track).
