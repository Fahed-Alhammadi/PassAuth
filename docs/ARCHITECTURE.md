# PassAuth Architecture

PassAuth is a self-hosted, zero-knowledge password manager. The server stores only ciphertext and can never read vault contents, item names, or URLs.

## Components

| Component | Tech | Notes |
|---|---|---|
| `crates/core` | Rust | All crypto, item model, importers. One implementation shared by every client. |
| `crates/server` | Rust (axum, tokio, sqlx) | REST API + WebSocket sync, SMTP, admin. Serves the web vault. |
| `crates/core-wasm` | Rust → WebAssembly | `core` bindings for the web vault and extension. |
| `web/` | TypeScript, React, Vite | Web vault, embedded into the server binary. |
| `extension/` | TypeScript, Chrome MV3 | Login, autofill, TOTP, passkey provider. |
| `crates/core-ffi` | Rust → UniFFI | `core` bindings (Kotlin and Swift) for the native apps. |
| `android/` (stage 2) | Kotlin, Jetpack Compose | Android app; see "Android app" below. |
| `ios/` (stage 2) | Swift, SwiftUI | iOS app; see "iOS app" below. |
| `desktop/` | Rust (Tauri 2) + the web vault | macOS, Windows and Linux app; see "Desktop app" below. |

### Why Rust
- Memory-safe without a garbage collector: fast, small container, low RAM.
- The same crypto code compiles to WASM (browser, extension) and native libraries (iOS, Android), so there is exactly one audited implementation of the vault format.
- Mature, audited crates: RustCrypto (`argon2`, `chacha20poly1305`, `hkdf`, `x25519-dalek`, `ed25519-dalek`), `opaque-ke`, `webauthn-rs`, `lettre`.

## Cryptography

### Account keys
```
master password ─┐
                 ├─ Argon2id (m=128 MiB, t=3, p=1, salt=random 16 B per account)
secret key (optional per user, 128-bit, in Emergency Kit) ─ HKDF ─ XOR ─► stretched key
stretched key ─ HKDF("passauth/auk/v1") ─► Account Unlock Key (AUK)
stretched key ─ HKDF("passauth/opaque-password/v1") ─► OPAQUE password input
AUK ─► decrypts Account Key (random 256-bit)
Account Key ─► decrypts X25519 keypair (sharing)
Vault Key (random 256-bit per vault) ─ wrapped by Account Key, or sealed to each member's X25519 key
Item Key (random 256-bit per item) ─ wrapped by Vault Key ─► encrypts item JSON
```
- Secret Key is **off by default**. Users turn it on in settings. (Planned, not built: an admin policy that requires it.) Enabling it re-wraps the Account Key under a new AUK; no vault data is re-encrypted.
- Cipher: **XChaCha20-Poly1305** everywhere. No unauthenticated modes, no legacy fallbacks.
- AEAD associated data binds `{format_version, item_id, vault_id}`, so ciphertexts cannot be swapped between items or fields.
- The whole item (name, URLs, username, password, TOTP, passkeys, notes, fields) is one encrypted blob. Plaintext on the server is limited to IDs, vault, revision, timestamps and sizes (the item type, folder and favorite are inside the ciphertext).
- Unknown item fields are kept (`extra` on every item struct) and a `format` above the client's own is never stamped down, so an older client editing an item written by a newer one doesn't erase the newer fields. Unknown enum values (e.g. a new URL match type) still fail to decode; add those behind a format bump.
- Item JSON carries a `format` number (`ITEM_FORMAT` in `crates/core/src/item.rs`). Clients upgrade older items when they decrypt them and stamp the current format when they encrypt. The server can't read items, so schema changes never need a server migration. Format 2 (0.2.1): a website's URL match `default` follows the client's "Default URI match detection" setting; older items, saved when `domain` was the implicit default, read as `default`.
- KDF parameters are authenticated: clients enforce minimums and refuse to log in with weaker parameters than they already know.

### Authentication: OPAQUE (`opaque-ke`)
- The server never receives the password or a hash it could crack offline.
- The AUK and the OPAQUE password input are two HKDF outputs of the same Argon2id result (domain-separated), so the server's OPAQUE record never yields the AUK. The OPAQUE export key is not used. Consequence: a leak of the `users.bundle` column alone allows offline guessing at Argon2id cost when the Secret Key is off, which is why the Secret Key is recommended.
- Sessions: opaque random access token (15 min) plus a **rotating** refresh token bound to the device, both stored SHA-256-hashed. Rotation is conditional on the presented token; presenting an already-rotated token revokes the session. Tokens go in the `Authorization` header; only `/api/ws` also accepts `?access_token=`, and a socket closes when its session is gone.
- 2FA: TOTP, email OTP, security keys / passkeys (WebAuthn), recovery codes. Wrong codes and failed security-key assertions are counted per account (10 per hour, then a 1-hour pause and an email alert), not only per sign-in attempt. New-device login sends an email alert.
- Security keys (`crates/server/src/passkeys.rs`, `webauthn-rs` "security key" ceremonies: user verification preferred, no resident key, no attestation check, ES256/ES384/RS256): the relying party is `DOMAIN` (RP ID = its host, allowed origin = the URL; behind a proxy it must be the public https address, else `GET /account` reports `passkeys_available: false` and the endpoints answer 400). Credentials are stored as webauthn-rs `SecurityKey` JSON in `passkey_credentials` (migration v4; counter and backup flags updated after each use, `last_used_at`), up to 10 per account; a `two_factor` row `provider = passkey` marks the method on while at least one exists, so login challenges list `"passkey"` among `providers`. Challenge state is kept in memory for 5 minutes like email codes: registrations in `App.passkey_registrations` keyed by a single-use `registration_id` (`POST /account/2fa/passkey/register/start` needs `x-reauth-token`, returns creation options with the user's other keys excluded; `…/register/finish {registration_id, name, credential}` stores the key and, as the first method, returns the recovery codes once; `DELETE /account/2fa/passkey/{id}` needs reauth), sign-ins inside the pending two-factor token (`POST /auth/2fa/passkey/start {two_factor_token}` → request options with `allowCredentials`; `POST /auth/2fa/passkey/finish {two_factor_token, credential, remember?}` → the same session and remember-device handling as `/auth/2fa/verify`). Only the web vault in a browser can register and use them (`web/src/lib/webauthn.ts`; the desktop app's WebView, the extension popup and the phone apps hide the method and point to a recovery code or the web vault), so the Settings page tells users to keep another method for those apps. A counter rollback on assertion (`CredentialPossibleCompromise`: the key may have been cloned) is logged at warn level with user and credential id and emails the owner, besides counting as a wrong code; `/auth/2fa/passkey/start` is limited to 20 challenges per account per 5 minutes. Any future admin "reset two-step login" must clear `passkey_credentials` together with the `two_factor` rows.
- Rate limits key on the TCP peer, or on `IP_HEADER` when the peer is a trusted proxy (`TRUSTED_PROXIES`, default loopback and private networks), using the right-most untrusted hop; IPv6 is bucketed by /64.

### Sharing (organizations)
- Vault keys are sealed to members' X25519 public keys. Sealed boxes are anonymous (not signed by the sharer); clients must therefore never pick a shared (`key_kind = sealed`) vault as the default save target, only the user's own `account` vault.
- Ownership comes only from creating a vault: `add_member` refuses `owner`, and nobody can change or remove a member at or above their own role. Membership changes, item writes and key rotation lock the vault row, and rotation re-checks members and items inside its transaction (each item exactly once).
- Public keys are shown as fingerprints for out-of-band verification, so a malicious server cannot silently substitute keys.
- Only clients can replace a vault key (the server never has it). Removing a member is one request, `POST /vaults/{id}/members/{user}/remove`, that carries the new key for every remaining member and every item re-encrypted under it, applied in one transaction with the removal (same checks as `/rotate`), so nobody is removed without the key change. When someone leaves on their own, is removed with the older `DELETE /vaults/{id}/members/{user}`, or deletes their account, the server sets `vaults.rotation_pending` (migration v5); `/sync` reports it and the web vault / desktop app shows owners and admins "Finish securing this vault" until one of them calls `/rotate`, which clears it.

## Features (stage 1: server + extension)
- Item types: Login (multiple URLs, TOTP, passkeys), Secure Note, Card, Identity, SSH Key. Plus custom fields, folders, favorites, trash, password history. (Planned, not built: attachments.)
- Password and passphrase generator. (Planned, not built: password health and a breach check via HIBP k-anonymity, run from the client only.)
- **Import** (client-side only; plaintext never reaches the server): export files from other password managers (JSON, password-protected JSON, CSV, `.1pux`, KDBX). Formats and field mappings: `docs/IMPORT_FORMATS.md`. **Export**: encrypted PassAuth JSON plus plaintext JSON/CSV.
- SMTP: verification, invites, new-device alerts, email 2FA, recovery, admin test mail.
- Admin panel: off by default, Argon2-hashed token, no shell or executable-path settings. "Reset two-step login" (`POST /admin/users/{id}/two-factor/reset`) is for a user who lost every method: it deletes their `two_factor` rows (authenticator, email, recovery codes, passkey marker), `passkey_credentials`, the failure counter and "remember this device" tokens, logs a warning and emails the user. The master password (and Secret Key) still protect the account.
- Real-time sync over WebSocket (`/api/ws`), plus a revision-date check for cheap polling.
- Website icons: `GET /api/icons/{host}` (unauthenticated, used as `<img src>`; clients fall back to a letter avatar on error). The server fetches the site's `<link rel=icon>` or `/favicon.ico` defensively: public DNS names only, every resolved IP must be public and the connection is pinned to it, redirects re-validated (max 3), ports 80/443, 5 s budget, 100 KiB cap, only PNG/ICO/GIF/JPEG/WebP by magic bytes (never SVG/HTML), `CSP: default-src 'none'`. Hits cached 7 days, misses 1 day (`ICON_CACHE_DIR`, default `icons/` beside the SQLite file). Uncached fetches are rate-limited per client IP (60/min) and capped at 8 concurrent. `ICON_SERVICE=off` disables it. Privacy: the server learns which sites' icons are requested (not which user, not vault contents); turn it off if that matters.
- Extension: login to any PassAuth server URL; autofill only on user action, in the top-level same-origin frame; inline save prompts; TOTP codes; acts as a WebAuthn **passkey provider** (ES256 keys stored inside the encrypted item, with fallback to browser or hardware keys).
- **Save rule** (the same in every client that offers to save; one pure, unit-tested function each: extension `background/save-plan.ts`, iOS `Shared/SaveLogic.swift`, Android `autofill/SaveRule.kt`). `U` = typed user name (trimmed, compared case-insensitively, may be empty), `P` = typed password, `C` = logins matching the page; "own" = writable and in the user's personal vault. (1) Logins in `C` with user name `U`: one already has `P` → nothing to offer; else a writable one → update it; else (read-only) nothing. (2) None and `U` not empty: an own login with an empty user name (only a password was saved; prefer the one whose password is `P`) → update it; none → new login. (3) None and `U` empty: `P` already saved for the page → nothing; exactly one own login → update it; otherwise a new login. An update writes the password (old one to the password history) and the user name only when one was typed. Rules 2 and 3 never pick a shared vault: anyone can add a user to a shared vault and plant a login with an empty user name there, which would otherwise collect what the user types (see Sharing). Clients with their own prompt (extension save frame, iOS save sheet, Android sheet) show "Save in": the own logins for the page (plus a rule-1 login in a shared vault, labelled with its vault) and "New login", preselected from the plan; what the prompt showed is what is applied, and only a target that this pending save offered is accepted. A rule-3 update is never applied without that prompt (where none can be shown, a new login is saved instead). Pending saves are bound to the account that captured them and dropped on lock, logout and account switch. The extension's prompt is an extension-origin frame (like the inline menu), so the page never sees vault item names or user names, and form capture needs a user gesture.
- **Prompts** ("decision sheet", every client): brand bar · context row (site tile, sentence-case title saying what is decided, domain beneath) · one grouped card of choices with a radio mark · verification directly above the actions · exactly one filled primary button, other actions as quiet text buttons. Tokens: spacing 4/8/12/16/24/32, radius 8/12/16 (web `app.css` `--space-*`/`--radius-*`/`--text-*`, iOS `PA.Space`/`PA.Radius`, Android `Theme.kt`). Shared parts: web `components/ui.tsx` (`Modal`, `ConfirmDialog`, `SheetActions`, classes `.sheet-*`, `.choices`, `.choice*`, `.tile`, `.btn-text`, `.setting*`, `.switch` — the extension popup depends on these names), extension `popup/sheet.tsx`, iOS `UI/DecisionSheet.swift`, Android `ui/components/DecisionSheet.kt`. Extension windows (passkey, unlock, pop-out) open centred over the requesting browser window and sized to their content (`shared/windows.ts`, maths in `shared/window-place.ts`).

## Android app (`android/`)
- Gradle project with two modules. `:core` is an Android library holding the UniFFI bindings (`io.passauth.core`) and `libpassauth_ffi.so` (arm64-v8a, x86_64), both generated by `scripts/build-android-core.sh` and gitignored, plus JNA. `:app` is the app (`io.passauth.app`, minSdk 34, compile/target 36). Crypto only ever comes from the Rust core; items, bundles and KDF params cross as JSON in the server/web shape (`app/.../data/Item.kt` mirrors `web/src/lib/types.ts`).
- Build: `scripts/build-android-core.sh && cd android && ./gradlew :app:assembleDebug :app:testDebugUnitTest` (JVM tests don't load the native library). Release: `./gradlew :app:bundleRelease`, signed only when `ANDROID_UPLOAD_KEYSTORE_PATH`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `ANDROID_UPLOAD_KEY_ALIAS` and `ANDROID_UPLOAD_KEY_PASSWORD` are set. Debug builds use the `io.passauth.app.debug` id.
- Version: `versionName` = `android/VERSION` (the Android app's own version; `scripts/release.sh android X.Y.Z`), `versionCode` = major·1 000 000 + minor·1 000 + patch (`android/buildSrc/src/main/kotlin/AppVersion.kt`, shared with the unit tests).
- Data layer (`app/.../data`): `VaultRepository` mirrors the extension's `background/vault.ts` (prelogin → OPAQUE → 2FA → bundle unlock → `/sync` → decrypt; create/update/trash; lock/logout; up to 5 accounts). `ApiClient` pins each request to one account and rotates refresh tokens on 401. `SecureStore` keeps tokens, settings and per-account data in a DataStore file encrypted with an Android Keystore AES-GCM key, plus an encrypted copy of the last `/sync` response (ciphertext) so the vault opens offline. Unlocked keys live only in memory as Rust handles.
- Unlock: master password (+ stored Secret Key), or biometrics: `Account.toSessionBytes()` (64 bytes) is wrapped by a per-account Keystore key that requires strong biometric auth and is invalidated when biometrics change. Vault timeout and action like the extension (`LockManager`); with "never" the session bytes are kept in the encrypted store.
- Hardening: no backup (`allowBackup=false`, extraction rules exclude everything), https only except `localhost`/`10.0.2.2` (network security config), `FLAG_SECURE` while unlocked or showing the Secret Key, clipboard copies marked sensitive and cleared after the user's delay, no secrets in logs.
- Autofill service (`app/.../autofill`, `PassAuthAutofillService`): `StructureParser` reads the AssistStructure (visible enabled text fields, `webDomain`/`webScheme`, only fields of the focused site's frame); `FieldClassifier` finds username/password/one-time-code fields from autofill hints, input type, HTML attributes and id/hint text (patterns of the extension's `fields.ts`). `FillTarget.resolve` decides what may match: web content in a browser on the privileged allowlist (package + signing cert) or in a WebView whose domain's asset links list the app → by website (`UrlMatcher`, default-match setting; scheme missing → https; Android gives no path, so "exact"/"starts with" see `scheme://domain/`); any other app → logins with the website `androidapp://<package>`; a browser's own UI and PassAuth itself → nothing. Web logins never match apps and vice versa; the extension's https→http downgrade refusal applies. The PassAuth server's own web vault is an ordinary website (a login saved for the server's address is offered and saved there). Unlocked: one Dataset per login (drop-down + keyboard inline suggestions via `androidx.autofill`) plus "Open PassAuth". Locked: one "PassAuth is locked" entry whose authentication IntentSender opens `AutofillAuthActivity`, which unlocks (master password or biometrics) and returns the datasets in `EXTRA_AUTHENTICATION_RESULT`. Logins with a TOTP get per-dataset authentication: picking one runs `AutofillAuthActivity` (see-through, no UI when unlocked), which returns the filled Dataset with a fresh code (also filled into a one-time-code field) and copies it when "Copy verification code automatically" is on — the only reliable hook for running code at the moment of selection. Save: `SaveInfo` (password required, username optional, save when the form disappears, "Never" button → never-save list keyed by base domain or `androidapp://<package>`); `onSaveRequest` applies the save rule (see Features; `SaveRule.kt`) when unlocked: new logins and rule-1/rule-2 updates silently, a rule-3 update only after the "Update login?" sheet (opened through the IntentSender); Android's save dialog carries a `CustomDescription` line saying whether a saved login will be updated or a new one added (chosen by conditions on the typed user name; only when the vault was unlocked at fill time and the place already has a login). Locked → returns an IntentSender to unlock first (credentials stay in memory, never in the intent), then an "Update login?" / "Save login?" sheet with "Save in" when there is something to choose; if Android can no longer open that sheet (the filled activity is gone), the pending save is applied at the next unlock of the same account within the 5-minute in-memory window (`SaveRule.withoutSheet`: a rule-3 update becomes a new login). Pending saves are bound to the account, removed on every exit and cleared on lock, logout and account switch; the consent sheets set `setHideOverlayWindows(true)` (permission `HIDE_OVERLAY_WINDOWS`). Passkey "Save in" (all clients) preselects only a personal-vault login for the exact host, else "New login"; shared-vault logins are listed with their vault's name. Respects "Ask to save and update logins". Always the active account.
- Credential Manager provider (`app/.../credentials`, Android 14+, `androidx.credentials`): `PassAuthCredentialService` offers a `CreateEntry` for ES256/platform passkey requests, `PublicKeyCredentialEntry`s for matching passkeys (rpId, allowCredentials or discoverable) and `PasswordCredentialEntry`s (same matching as autofill); locked → an `AuthenticationAction`. `CredentialActivity` does the work after the user picks: origin check (`Origins`): privileged callers' origin from `CallingAppInfo.getOrigin(allowlist)` with `res/raw/privileged_allowlist.json` = Google Password Manager's published list (https://www.gstatic.com/gpm-passkeys-privileged-apps/apps.json, linked from the provider guide; Chrome stable/beta/dev/canary, Firefox, Edge, Brave, Samsung, …) and the RP ID checked against the origin like the extension's `effectiveRpId`; apps get `android:apk-key-hash:<b64url sha256(cert)>` and must be listed in `https://<rpId>/.well-known/assetlinks.json` (`delegate_permission/common.get_login_creds`, package + cert fingerprint; https, no redirects, 5 s, 256 KiB, cached 1 h; `include` not followed) or the request is refused. User verification: unlocking in the flow counts, otherwise BiometricPrompt (biometric or screen lock). excludeCredentials is checked after consent (InvalidStateError). Keys and signatures come from the core (`passkeyCreate`/`passkeyAssert`); clientDataJSON is built with `passkeyClientDataJson` for apps (and hashed), while browsers' `clientDataHash` is signed as given and the built JSON is only the placeholder the guide asks for. Responses are WebAuthn JSON; passkeys are stored like the extension's `storePasskey` (same fields, counter 0, discoverable), on the same site+username login or a new login for `https://<rpId>`.
- Settings → Autofill shows whether PassAuth is the autofill service and the passkey provider, with buttons to Android's settings, plus default URI match, TOTP copy, clipboard clearing, "Ask to save and update logins" and the never-save list. Debug-only test hooks (gradle properties, never in release builds): `passauth.testAssetLinksBase` (asset links from a local server) and `passauth.testPrivilegedApp` (trust one more browser, e.g. a Chromium snapshot). `:samples:login` is a debug-only test app (login form + Credential Manager calls), not part of the app or its bundle.
- Account deletion (Google Play requirement): Settings → About → Delete account. The master password is proven to the server with an OPAQUE login with `purpose: "reauth"` on the signed-in session (like the web vault's `reauth`), then `DELETE /api/account` with `x-reauth-token`; the account is then forgotten locally like Log out (biometric key, offline copy, stored Secret Key and two-step remember token removed; the last account keeps only the server address).
- Item editor TOTP field: type, "Paste" (clipboard) or "Scan QR code" (CameraX preview + ImageAnalysis, latest frame only, decoded in memory by ZXing core; no Play services; frames are never stored and the luminance buffer is wiped on close; the preview is a TextureView inside a dialog that inherits FLAG_SECURE). The `CAMERA` permission is requested only on tap; denial shows how to type or paste the key and a link to Android settings. `otpauth://totp/…` URIs are stored whole (scheme lower-cased for the core), plain base32 keys cleaned (upper case, no spaces); `OtpAuth` mirrors the core's TOTP checks so accepted keys always produce codes. HOTP and `otpauth-migration://` are refused with an explanation.
- Item page: "Password history" (count) opens the previous passwords (`password_history`, newest first, masked with reveal and copy). The overflow menu moves an item to another vault where the user is owner, admin or writer: re-encrypted with the target vault key under the same id and `PUT /api/items/{id}` with the new `vault_id` and the old revision (the web vault's `updateItem(entry, item, vaultId)`).
- Live sync (`LiveSync`): while MainActivity is started and the active account is unlocked, a WebSocket to `/api/ws?access_token=…` (OkHttp, 25 s pings). `{"type":"sync","revision":N}` with N above the shown revision re-syncs; `{"type":"logout"}` makes the app check its session (an ended one signs the account out through the refresh-token path). Disconnects on background, lock or account switch; reconnects with backoff (1 s doubling to 60 s, jitter), each time first calling `/sync/revision` so an expired access token is refreshed and missed changes are caught up. The item editor keeps the item as it was when editing started, so a live update during editing surfaces as the usual revision conflict instead of being overwritten.
- Background sync (`data/BackgroundSync.kt`; Settings → Vault options → "Background sync": Off/30 min/1 h/2 h (default)/6 h/12 h, `Settings.backgroundSyncMinutes`): WorkManager unique periodic work `background-sync` (interval = setting, flex ≤ 15 min, constraints connected + battery not low; `PassAuthApp` re-schedules it from the state flow on start, setting change, sign-in and last sign-out) runs `VaultRepository.refreshAllCaches()` in the app's own process: the active account, if unlocked, gets a normal `syncLocked()`; every other signed-in account gets `refreshCacheLocked` = GET `/sync` through the usual `ApiClient` (same refresh/401 path, so no parallel refresh that the server would flag as token reuse), `CacheRefresh.revisionOf` checks the body is a snapshot (numeric revision, bundle, vaults, items) and `shouldWrite` that it isn't older than the cached copy, then the ciphertext is stored as is with `lastSync`/`bundle`/name. Nothing is decrypted or kept in memory; the next unlock is cache-first and sees the fresh copy. Retried only when every account hit a network error.
- Export: Settings → Vault options → Export vault. Formats come from the core (`exportVaultEncrypted` (≥10-character export password, Argon2id), `exportVaultJson`, `exportVaultCsv` (logins and notes only)), with warnings for the unencrypted ones. The master password is checked locally against the bundle first; the file is written only to the location the user picks with `ACTION_CREATE_DOCUMENT` (`passauth-export-YYYY-MM-DD[-protected].json` / `.csv`).
- Account security (Settings → Account security, `ui/settings/AccountSecurityScreens.kt` + `SecurityViewModel`; request logic in `data/AccountSecurity.kt`, JVM-tested with a fake server and fake crypto, `CoreSecurityCrypto` = the core): "Change master password" mirrors the web vault's `changeKeys` (reauth → `Account.rewrap` → `/account/keys/start` → `opaqueRegisterFinish` → `/account/keys/finish` with `x-reauth-token`), with the web meter (Weak <50 bits, asked again before use; Fair/Good/Strong at 50/65/80) and a Secret Key choice (keep / turn on / turn off; also a separate Turn on/off with the master password). Afterwards `Stored.afterKeyChange` replaces the stored bundle and Secret Key (removed when turned off) and drops the two-step remember token; the session, biometric blob and "never" keys hold the account key, which a re-wrap keeps, so they stay valid; a sync refreshes the offline copy. A new Secret Key is shown once (Copy, Emergency Kit PDF via `PdfDocument` saved with SAF, "I saved it" before Done). "Two-step login" reads `GET /account`: authenticator setup (QR drawn from ZXing's encoder, grouped setup key, Copy, `otpauth://` intent), email codes, regenerate recovery codes and turn a method off (both after reauth); recovery codes are shown once in a dialog that back/outside can't close until "I saved them" (Copy all, Share, Save). Secrets stay in the ViewModel (never the saved-instance state) and are dropped when the screens are left.
- Web vault shortcuts open the account's server in the browser with path routes: Vault options → `/settings/vaults`, `/import`, `/vault`.
- Permissions (`app/.../ui/permissions`): on a first launch (never shown and no server connected yet; flag in `Stored.onboarding`, shared by all accounts) "Set up PassAuth" comes before the connect screen and lists only what the app uses, each optional with its own button: camera (runtime permission), autofill service and passkey provider (`SystemServices`, Android's settings screens), fingerprint / face unlock (`BiometricManager`; nothing to grant, so choosing it there offers biometric unlock once after the next sign-in or unlock, with one biometric confirmation; "Set up" opens enrollment when none is enrolled). "Continue" or "Skip for now" mark it shown. Settings → Permissions shows the same list with each state; `PermissionModel` maps the camera to Allowed / Not allowed / Not asked / blocked ("Open settings" → app details) from granted + `shouldShowRequestPermissionRationale` + whether PassAuth ever asked (`onboarding.cameraAsked`, also set by the TOTP scanner). No notifications, location or contacts. Android 17's local network permission applies only to apps targeting SDK 37+ (with target 36 it comes with INTERNET), so it's not listed yet.
- Accessibility: icon buttons have content descriptions, card titles and page titles are headings, label + value rows are read as one node before their actions, masked secrets read as "hidden", text drawn inside fixed shapes (avatar, TOTP ring) doesn't scale with the font, select fields wrap. Checked at font scale 2.0.

## iOS app (`ios/`)
- Xcode project generated by XcodeGen from `ios/project.yml` (`PassAuth.xcodeproj` is not committed). Targets: `PassAuthCore` (framework: the UniFFI Swift bindings `ios/Core/Sources/PassAuthCore.swift` plus the static `PassAuthCoreFFI.xcframework`, device arm64 + simulator arm64, both generated by `scripts/build-ios-core.sh` and gitignored), `PassAuthKit` (framework, extension-safe API only: the data layer, shared with the AutoFill extension), `PassAuth` (SwiftUI app, `io.passauth.app`, iOS 17+, iPhone and iPad), `PassAuthAutoFill` (credential provider extension `io.passauth.app.autofill`, embedded in the app; theme and form components come from `ios/UI`, compiled into both), `PassAuthTests` (XCTest, hosted) and `PassAuthUITests` (XCUITest). Swift 6 language mode with complete concurrency checking (the generated bindings build in Swift 5 mode). Crypto only ever comes from the Rust core; items, bundles and KDF params cross as JSON in the server/web shape (`Shared/Item.swift` mirrors `web/src/lib/types.ts`: lenient decoding, nulls written, unknown `format` omitted).

- Data layer (`ios/Shared`): `VaultRepository` (`@MainActor`, `@Observable`) mirrors the Android repository and the extension's `vault.ts` (prelogin → OPAQUE → 2FA with remember-device → bundle unlock → `/sync` → decrypt; register; create/update/trash/restore/delete forever with revision conflicts reported as `ConflictError`; lock/logout; up to 5 accounts). Operations are serialised by an async lock; Argon2id and decryption run off the main thread. `ApiClient` (ephemeral `URLSession`, no cache/cookies, redirects refused) pins each request to one account and rotates refresh tokens on 401.
- Storage (`SecureStore`): accounts, settings and device id in `state.bin`, and each account's last `/sync` response in `vault/<id>.bin`, in the App Group container (`group.io.passauth.app`, falls back to Application Support without the entitlement), encrypted with ChaCha20-Poly1305 under a random Keychain key (file name as associated data), file protection complete, excluded from backup. Tokens, Secret Keys, two-step remember tokens and (vault timeout "never") session bytes live in one Keychain item. All Keychain items are `WhenUnlockedThisDeviceOnly`, non-synchronizable, in the shared access group `$(AppIdentifierPrefix)io.passauth.shared` listed in both targets' entitlements and copied into their Info.plist (`PAKeychainGroup`): `JEXQBK3SQ5.io.passauth.shared` when signed with the team, `io.passauth.shared` in unsigned simulator builds (the simulator honours the embedded entitlements). A missing `state.bin` (fresh install) deletes leftover Keychain items. The state is read once the UI is up.
- App ↔ extension (two processes on the same files and Keychain item): every `SecureStore.update` re-reads `state.bin` and the secrets under a cross-process `flock` (`.state.lock`, 2 s timeout) before writing, so neither side overwrites the other; the app calls `reload()` when it becomes active. Only the app creates the state, the store key or wipes them (`Role.appExtension` never does). Refresh tokens rotate and a reused one revokes the session, so a refresh runs under a per-account lock (`.refresh-<id>.lock`, 25 s wait, 20 s request), re-reads the tokens, and calls `/auth/refresh` only if the stored access token is still the rejected one (otherwise the other process already rotated them). The app holds that lock inside a background task (iOS kills apps suspended while holding a shared-container lock). A refresh that can't reach the server no longer signs the account out.
- Unlock: master password (+ stored Secret Key), or Face ID / Touch ID: `Account.toSessionBytes()` in a Keychain item with `SecAccessControl` `.biometryCurrentSet` (invalidated when enrolment changes; the app then turns biometric unlock off and asks for the master password). Vault timeout and action like the extension and Android (`LockManager`: continuous clock, touches tracked by a non-interfering window gesture recognizer, "Immediately" fires when the scene goes to the background, "On app restart" keeps keys in memory only, "never" keeps session bytes in the Keychain).

- Tauri 2 shell around the web vault: `desktop/src-tauri` (Rust, its own Cargo workspace so the root workspace, Docker image and `cargo test --workspace` never see it) and `desktop/src` (TypeScript entry that imports `web/src` through the `@web` alias, like the extension; React deduped). Choosing one opens the web vault's editor through `web/src/lib/drafts.ts` (`openDraft(itemId, apply)`: the vault page shows that item's editor with the change applied; `Shell` drops the draft when the route leaves that item and the desktop drops it when the vault stops being unlocked; if the open editor has unsaved changes (`ItemEditor` `onDirtyChange`) the desktop asks "Discard your changes?" first; nothing is saved until the user saves; browser and extension never open a draft). Capability: `deep-link:allow-get-current` only.
- Updates: `tauri-plugin-updater` with the minisign public key in `tauri.conf.json` and endpoint `https://github.com/Fahed-Alhammadi/PassAuth/releases/latest/download/latest.json` (GitHub's "latest" skips pre-releases). Checks 10 s after launch, at most once a day (silent unless an update exists), and on demand (menu, tray, Settings → About). The flow is in-app on the web vault's `Modal` (`desktop/src/updater.tsx`): checking → "You're on the latest version" / "PassAuth X.Y.Z is available" with Install and restart / Not now → progress ("PassAuth closes and reopens when it's done.") → relaunch; failures show "Couldn't check for updates…" with the raw error behind a Details disclosure, and once the user confirmed an install every error is shown. Never installs without confirmation. The private key is GitHub secret `TAURI_SIGNING_PRIVATE_KEY` (copy in `Keys/`); losing it means installed apps can't verify any future update.
- Vault timeout (`desktop/src/timeout.ts`; Settings → Account → "Vault timeout", a card the web vault renders only when the `vaultTimeout` hook is present): the extension's options and meaning. Minutes (default 15) count from the last keyboard/mouse activity in the window, deadline-based so a hidden window (throttled timers) still locks on its next tick or when shown; "Immediately" locks when the window is closed to the tray or minimised; "On system lock" (macOS only: `watch_system_lock` in `lib.rs` observes `NSWorkspaceWillSleepNotification`, `NSWorkspaceSessionDidResignActiveNotification` and the distributed `com.apple.screenIsLocked`, emitting `system-lock`; Windows/Linux have no observer yet, so the option isn't offered there); "On app restart" keeps keys in memory only; "Never" stores the account session bytes in the keychain as `pa.keys` (host-scoped like the other secrets) and `applyTimeoutAtStart` opens the vault with them after `boot()`. Timeout action lock (default) or sign out; with sign out, a restart signs out (as the extension does). The web vault's own 15-minute idle lock (`useAutoLock`) is skipped when the hook exists. `pa.keys` is removed whenever the vault leaves "unlocked" (⌘L, menu, tray, timeout), on sign-out (server rejection or the user), on change server and when the setting leaves "never"; a server that can't be reached keeps it (status "unreachable", or `UnreachableError` from the restore's sync), and the restore is retried every 30 s and after each `boot()` ("Try again"). The sign-out action locks (keys dropped, `pa.keys` removed) before calling `/auth/logout`. `desktop/src/secrets.ts` serialises keychain calls per entry name, so a delete issued right after a set can't overtake it on the blocking thread pool; `secretStore.set` returns the keychain promise so lock paths await the wipe. Without a keychain (`keychainAvailable()` false: WebView-storage fallback) "Never" is disabled in the card ("Not available: this computer has no keychain service") and keys are never persisted. Setting lives in WebView localStorage `desktop.vaultTimeout`, per install. Keychain entries are filed under the bundle identifier (`app.config().identifier`, = `io.passauth.desktop`), so a test build with another identifier never touches the real app's secrets.
- "This app" (`desktop/src/app.ts`, hook `DesktopHooks.app`, card in Settings → Account): **Start at login** = an OS login item through `tauri-plugin-autostart` (macOS LaunchAgent, Windows registry Run key, Linux autostart .desktop) that launches the app with `--hidden`, so `build_window` creates the window invisible and the app sits in the tray (macOS: accessory policy until the window is opened); the card shows the OS's answer (`isEnabled`), and when it is on the app calls `enable()` again once per launch, because the login item stores the executable's path and `isEnabled` only checks that the entry exists (a moved app or a hand-downloaded AppImage would otherwise leave a dead login item that still shows as on). An update restart keeps this run's arguments (`relaunch`, and the Windows installer's `/ARGS`), so `installUpdate` first calls `prepare_relaunch` (one-shot `showNextLaunch` in `shell.json`): the next launch shows the window even with `--hidden`, and the flag is cleared when consumed or when the install failed. A second launch (single-instance plugin) shows the window unless it carries `--hidden` itself. **Keep the Dock icon** (macOS only, default off, see above). **Background sync** (default every 2 hours; Off/30 min/1 h/2 h/6 h/12 h, localStorage `desktop.app`): the live WebSocket pushes changes while unlocked, but can die silently after sleep or a network change, so while the vault is unlocked a one-minute ticker calls `resync()` (`web/src/lib/vault.ts`: `/sync/revision` first, which also refreshes an expired access token, then reopen the socket, then `sync()` if the server is newer) on the schedule, when a tick arrives more than 5 minutes late (the computer slept), on macOS `NSWorkspaceDidWakeNotification` (`system-wake` from `watch_system_lock`), and when the window becomes visible/focused if the last check is older than 5 minutes. Nothing runs while locked: desktop keeps no offline copy.
- Resource use: the hidden window keeps its webview (closing = `hide()`, so the account keys in wasm memory survive; destroying it would be a lock). While unlocked the live WebSocket is the only connection; when it drops, the reconnect delay starts at 3 s and doubles to 2 min (jitter, reset on open and on `resync()`), and while `navigator.onLine` is false nothing is retried until the `online` event. Timers while hidden: the one-minute background-sync ticker and the 30 s timeout ticker, both only while unlocked; nothing animates. `desktop/src-tauri/Cargo.toml` has its own `[profile.release]` (LTO, one codegen unit, stripped, `opt-level = "s"`, `panic = "abort"`) because the crate is outside the root workspace. Fonts: only the latin and latin-ext IBM Plex subsets are bundled. Measured 2026-11-09 on macOS, idle in the tray for 8 h: host process 35 MB footprint, WebKit content process 70 MB, GPU + networking helpers 28 MB, 0% CPU.
- Keychain hygiene: entries are `<host>|pa.*` under service `io.passauth.desktop`; **Change server** deletes the old host's `pa.email`, `pa.sk.<email>` and `pa.remember.<email>` besides the session and persisted keys, so servers the user left don't accumulate entries. Sign-out keeps `pa.sk`/`pa.remember` for the same server on purpose.
- Signing: macOS builds are signed with the Developer ID Application certificate (`APPLE_CERTIFICATE` + `APPLE_CERTIFICATE_PASSWORD`, p12 with Apple's intermediate; copy in `Keys/`) and notarized with the App Store Connect API key secrets; without the certificate the build is unsigned and Gatekeeper warns. Windows builds are unsigned (SmartScreen warns) until a code-signing certificate is added. Linux: AppImage (updatable), .deb and .rpm.
- Build: `scripts/build-wasm.sh web/src/wasm && (cd web && pnpm install) && cd desktop && pnpm install && pnpm tauri dev` (web deps are needed because `web/src` imports resolve from `web/node_modules`) (against a `http://localhost:8091` throwaway server, typed with the scheme) or `pnpm tauri build`. Version in `desktop/package.json` + `desktop/src-tauri/Cargo.toml` (`tauri.conf.json` has none). Icons in `src-tauri/icons` were generated with `pnpm tauri icon` from a square render of the logo.

### macOS AutoFill extension (`desktop/macos/`)
- Native credential provider `PassAuthAutoFill.appex` (`io.passauth.desktop.autofill`, display name PassAuth, macOS 14+ while the host app runs from macOS 12 (`minimumSystemVersion`): on 12/13 the appex is simply absent and the app works without AutoFill), embedded at `PassAuth.app/Contents/PlugIns/`; listed in System Settings → General → AutoFill & Passwords. Capabilities: ProvidesPasswords, ProvidesPasskeys, ProvidesOneTimeCodes (macOS 15), ShowsConfigurationUI. No save/generate requests (iOS 26.2 only, unavailable on macOS).
- Ported, not forked: XcodeGen project `desktop/macos/project.yml` builds `ios/Shared` as the static library `PassAuthKit` (minus `QrDecoder.swift`), the UniFFI bindings as `PassAuthCore` (static, from `scripts/build-macos-core.sh`: universal arm64 + x86_64 `desktop/macos/Core/PassAuthCoreFFI.xcframework` + `Core/Sources/PassAuthCore.swift`, gitignored, same bindgen as iOS), and the appex from `ios/AutoFill/AutofillModel.swift` (the whole request flow: matching, fill, TOTP copy, passkey create/assert, one-time codes, identity store sync), `ios/UI/Theme.swift` (colours, logo) and the macOS-only `desktop/macos/AutoFill/` (`NSViewController` subclass hosting SwiftUI in `NSHostingView`, 460×560 sheet; `MacViews.swift`, `MacSignIn.swift`, `TimedUnlock*.swift`). Platform differences in shared code are `#if os(iOS)` / `os(macOS)` / `#available(iOS 18.0, macOS 15.0, *)`; the iOS build is unchanged.
- Self-contained (shares no session with the Tauri app; see the hand-off below): its own sign-in in the configuration UI and in the sheet when signed out (server with the iOS https/LAN-http rules and confirmation, email, master password, Secret Key, two-step login with remember-this-Mac), its own device on the server ("PassAuth for Mac AutoFill", kind `desktop`), unlock with master password or Touch ID (`.biometryCurrentSet` item), settings (gear button / configuration screen: vault timeout, Touch ID, TOTP copy, default URI match detection (same options and help as iOS Settings → AutoFill, per device; a change rewrites the identity store), lock now, sign out). `SecureStore` runs with `role: .app` (it owns its state); files live in the extension's sandbox container (Application Support; no App Group, no file-protection class on macOS), secrets in the data-protection Keychain (`kSecUseDataProtectionKeychain`) under its own group `JEXQBK3SQ5.io.passauth.desktop.autofill` (Info.plist `PAKeychainGroup`). Clipboard: `NSPasteboard` marked concealed + transient; never cleared by the extension (its process ends right after the request, so the clearing delay is ignored on macOS and the settings say so).
- Vault timeout: macOS starts the extension per request, so the unlocked keys (session bytes) are kept in its Keychain with a deadline that slides on each use (`TimedUnlock`, rules in `TimedUnlockPolicy`, unit-tested): "Immediately" keeps nothing, "Never" uses the repository's persisted keys, "On app restart" isn't offered. Lock now / sign out remove them.
- Desktop → extension hand-off (2026-11-09): the extension's separate sign-in confused users ("the app is running, why connect again?"). The Tauri app now leaves a Keychain item in the extension's access group (`keychain-access-groups` in `entitlements/macos-host.plist`; data-protection keychain via `security-framework`, service `io.passauth.desktop.handoff`, account `handoff`, its own service so the extension's fresh-install `Keychain.deleteAll` keeps it) with JSON `{server, email, secretKey}` whenever the vault is unlocked (`desktop/src/handoff.ts` → command `autofill_handoff`; `{}` on Change server). Never tokens or vault keys: the extension must get its own session (a shared refresh token would be flagged as reuse by the server and end both sessions). `MacSignIn` reads it (`Keychain.readDesktopHandoff`, `DesktopHandoff`): with no server yet it connects to the handed-over server by itself (`setServer(allowLanHttp: true)`: plain http was already accepted in the app) and shows the login step with email and Secret Key filled and a notice, so only the master password is typed; a signed-out extension also gets email + Secret Key prefilled when the hand-off is for its server. Everything after that (Touch ID, timed unlock, its own device on the server) is unchanged.
- Identity store on macOS (2026-11-09): nothing but the extension writes `ASCredentialIdentityStore` there (on iOS the app does too), and macOS ends the extension right after a request, so `AutofillModel` answers the system (`handOver`: complete, cancel, configuration done) only after `repo.identities.flush(timeout: 2 s)`; before that fix the write started by the unlock/sync was killed with the process and Safari only ever offered the full list instead of the site's logins. `CredentialIdentitySync` skips a write when the records' fingerprint equals the last one written; since every request is a fresh process, that fingerprint is persisted (`StoredFile.identityFingerprint`, set by `onWritten` only after the system store took the write, "" after it was emptied, cleared by `invalidate()`) and seeded on the first `refreshIdentities()`, so an unchanged store isn't rewritten (and waited for) on every request. Shared with iOS, where the app and the extension write the same store. Diagnostics (counts only) in the unified log, subsystem `io.passauth.autofill` (categories `requests`, `list`, `identities`): `log show --last 10m --predicate 'subsystem == "io.passauth.autofill"'`.
- Build: `desktop/macos/build.sh` → `desktop/macos/build/PassAuthAutoFill.appex` (Release, universal; runs `scripts/build-macos-core.sh` if the core is missing; version = `desktop/package.json`, build number as iOS). Signed when `MACOS_SIGN_IDENTITY` is set (+ `MACOS_AUTOFILL_PROFILE` = the Developer ID provisioning profile, copied to `Contents/embedded.provisionprofile`; optional `MACOS_SIGN_KEYCHAIN`), with hardened runtime, timestamp and `desktop/macos/AutoFill/AutoFill.entitlements` (sandbox, network client, AutoFill, Keychain group, application/team identifier); otherwise ad hoc with `AutoFill-adhoc.entitlements` (sandbox + network only: builds, but macOS won't use it). The profile accepts only the certificate it was made for (the `APPLE_CERTIFICATE` p12, SHA-1 F81B…); another Developer ID certificate gets the appex killed by AMFI ("No matching profile found"). Tests: `cd desktop/macos && xcodegen generate && xcodebuild -scheme PassAuthAutoFill -destination 'platform=macOS' test` (TimedUnlockPolicy + the shared UrlMatcher/ItemJson/OtpAuth/Autofill tests from `ios/Tests` on macOS).
- The containing app needs the AutoFill entitlement too: System Settings skips a credential provider whose host app lacks `com.apple.developer.authentication-services.autofill-credential-provider` (log: "Skipping extension … because its containing app is missing the … entitlement"; seen 2026-11-08 on macOS 27). So the Tauri app is signed with `desktop/src-tauri/entitlements/macos-host.plist` (application-identifier `JEXQBK3SQ5.io.passauth.desktop`, team-identifier, the AutoFill entitlement; no sandbox) and carries its own Developer ID profile for App ID `io.passauth.desktop` (capability AutoFill Credential Provider) at `Contents/embedded.provisionprofile` (`Keys/MACOS_DESKTOP_PROVISIONING_PROFILE.provisionprofile`, secret of the same name); without the profile, or signed with a certificate the profile doesn't name, AMFI kills the app at launch ("No matching profile found"). Both are CI-only config like the appex.
- Packaging (desktop CI): build and sign the appex before `tauri build`, put it at `PassAuth.app/Contents/PlugIns/PassAuthAutoFill.appex` (e.g. `bundle.macOS.files` `"PlugIns/PassAuthAutoFill.appex"`), sign the app with the host entitlements + embedded profile (`bundle.macOS.entitlements`, `files` `"embedded.provisionprofile"`), and sign inside-out: the appex first (build.sh), then the app without `--deep` (`codesign --force --timestamp --options runtime --sign <id> PassAuth.app`; `--deep` would re-sign the appex without its entitlements and profile), then notarize and staple. Check with `codesign --verify --deep --strict PassAuth.app` and `codesign -d --entitlements - PassAuth.app/Contents/PlugIns/PassAuthAutoFill.appex`.

## Deployment
- One container image `ghcr.io/fahed-alhammadi/passauth` (server + web vault), tagged `X.Y.Z` and `latest`, with multi-arch builds (amd64, arm64).
- `docker compose up` gives the server, with SQLite in `/data` by default and PostgreSQL optional via `DATABASE_URL`.
- Config via env or `*_FILE` secrets. See `.env.example`.

## CI/CD (GitHub Actions)
- CI = one workflow per product holding both its checks and its release (`.github/workflows/`): `core.yml` (fmt, clippy, tests on SQLite + PostgreSQL, `cargo audit` of the root lockfile, also weekly; no release), `server.yml` (amd64 + arm64 image, not pushed; release = GHCR publish), `extension.yml` (web vault + extension build and tests; release = zip + Chrome Web Store), `desktop.yml` (desktop app check, `cargo audit` of `desktop/src-tauri`, macOS AutoFill extension unit tests; release = installers + GitHub release), `android.yml` (debug build + unit tests; release = Play bundle), `ios.yml` (simulator build; release = TestFlight archive). Check jobs run on pushes to main and PRs only when the product's own files or the code it is built from change (`paths:`); a change to `crates/` or `Cargo.*` runs all of them, a change to one app runs only that app's. Release jobs run only on that product's tag (GitHub ignores `paths` for tag pushes) or "Run workflow", never on branch pushes or PRs. Concurrency group = workflow + ref: check runs on a branch replace each other, tag runs are never cancelled.
- Versions: five parts, each with its own version and tag; bump one with `scripts/release.sh <part> X.Y.Z` (commits only that part's version files and tags it), push main, wait for CI, push the tag. A shared core change ships in whichever parts you release.
  - server + web vault: root `Cargo.toml` `[workspace.package] version` (+ `web/package.json`) → tag `server-X.Y.Z` → `server.yml`: multi-arch image to GHCR as `X.Y.Z` + `latest` (pre-releases `X.Y.Z-rc.N` don't move `latest`), no GitHub release: `scripts/release.sh server` adds the notes from `scripts/release-notes.sh` (commits since the previous `server-` tag touching server paths) to `CHANGELOG.md` in the release commit. GitHub releases are used only by the desktop app.
  - extension: `extension/package.json` + `public/manifest.json` → `extension-X.Y.Z` → `extension.yml`: builds `passauth-extension-X.Y.Z.zip` (kept on the run as an artifact) and submits it to the Chrome Web Store, which needs a higher manifest version per upload. The extension and apps get just a tag.
  - iOS: `ios/VERSION` → `ios-X.Y.Z` → `ios.yml` (TestFlight). Android: `android/VERSION` → `android-X.Y.Z` → `android.yml` (Play track from repo variable `PLAY_TRACK`: `internal` when unset, `alpha` = closed testing; manual runs can pick one). Build number / versionCode = major·1 000 000 + minor·1 000 + patch, so every store upload needs a higher version. Old `vX.Y.Z` tags (≤ 0.4.3) released all parts together; `<part>-vX.Y.Z` tags were used until 2026-11-05.
  - desktop: `desktop/package.json` + `desktop/src-tauri/Cargo.toml` (+ `Cargo.lock`) → tag `vX.Y.Z` → `desktop.yml`: macOS universal (signed + notarized when the Apple secrets exist), Windows x64 NSIS, Linux AppImage/deb/rpm, built with `tauri-apps/tauri-action` into a GitHub release marked Latest with `latest.json` for the updater (pre-releases `X.Y.Z-beta.N`: prerelease, no `latest.json`), plus fixed-name copies (`PassAuth-macOS.dmg`, `PassAuth-Windows-x64-setup.exe`, `PassAuth-Linux-x86_64.AppImage`, `-amd64.deb`, `-x86_64.rpm`) for stable download links. Manual runs build only. CI job `desktop` typechecks, builds the frontend and runs clippy on Ubuntu.
- Stage 2: `ios.yml` (xcodebuild archive + upload to App Store Connect / TestFlight) and `android.yml` (signed bundle to the Play Console internal track).
